# 025 把 024 的修复补进正式测试套件

## 背景

024 修了两处缺陷，但验收用的是一次性脚本，正式测试文件里没有对应用例。
按我们定过的规矩，没被测守住的功能，以后改坏了也发现不了。本轮补上。

## Prompt

```
我又发现一个问题想请你帮忙。

上次你帮我改的那个抽取模块，落款日期不再被当成截止日期了，地点带圆括号的也能抽完整了，我跑测试也都通过了。可是我发现正式的测试文件里，这两类一条用例都没有。也就是说这两个功能现在虽然是对的，但是没有被测试守住，以后要是不小心改坏了也发现不了。

我想请你在正式那个测试文件里把用例补上。第一类是落款日期不能被当成截止日期，比如通知结尾写单位然后换行写日期，或者日期和单位写在同一行，还有落款写在开头那两种情况，这几种的截止日期期望值都要写成空。第二类是只有一个日期但它是真的截止日期，比如写的是请于六月二十日前把表交上去这种，这个必须还能抽出来，不能因为改了落款判断就把它也弄没了，再比如正文有一个真截止日期同时结尾还有落款日期的，要抽到正文那个不是落款那个。第三类是地点带圆括号的，比如写到学院教学办公室然后圆括号文科楼二零八，期望值要包含门牌号还要完整，再比如圆括号A三零一办公室这种。第四类是地点后面跟着动作词的，比如写到宿舍管理中心值班室登记领取，期望值只能是宿舍管理中心值班室不能提前截断。

有个地方我特别提醒你。有一条通知里写的是学校决定在全校范围内开展宿舍安全隐患大排查，后面还有一句是于本周五前将排查表交至保卫处值班室。这一条的期望值是保卫处值班室，不是全校范围内。之前有一版改动把这个抽错了，抽成了全校范围内，原因是在判断整串是不是含动作词之前先把动作词那一段切掉了，剩下的看着像个正常地点就提前返回了。所以这一类一定要写成期望保卫处值班室。

还有几点。用例要多跑几个不同的通知原文，不要只用一个。要有故意写错的用例，而且它必须真的会报错，不能永远显示通过。测试要直接引用真正的那个模块，不要自己另外抄一份相似的来判断。那个存各种命令的文件里原有的命令一条都不能删，特别是那条查密钥的，改完请把所有命令都跑一遍把结果一起给我。如果我给的信息不够你写期望值，你可以按照语义自己算，但是如果你发现原来某个用例的期望值本身写错了，不要直接改成实际值了事，要跟我说一声。

回复的时候不要把这个文件整个重新输出一遍，只要告诉我改动落在哪几行，把改之前和改之后的那几行分别写出来，我自己去替换。如果改动分散在好几处，就一处一处分开说清楚，每处都标明大概在第几行。

我不太懂测试怎么组织，如果哪里说得不对，你按你的判断来就好。
```

## 验收要点（本机侧）

1. 改动只落在测试文件，生产模块 `extractNotice.js` 不得被改
2. 新增用例数不少于 12 条，覆盖上述四类
3. 注入验证：令 `isSignatureDate` 永远返回 false，落款类用例必须报红
4. 注入验证：恢复"先截断再判"的旧写法，保卫处值班室用例必须报红
5. 全量 13 条离线命令 exit=0
