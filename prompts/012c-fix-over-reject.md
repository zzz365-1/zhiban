# 012c 修判据过度拒绝

**立项**：2026-10-31 20:55
**定位**：012b 改对了方向，但矫枉过正——修好了两条用例，却把正常单条通知也拒了。

## 本机注入验证（未采信 18 全绿）

012b 后 `test:batch` 为 18 通过 / 0 失败，且**改的是判据不是测试数据**（新增
`looksLikeMultipleNotices`，四条规则），方向正确。

但用真实语料注入四条场景验证，第四条暴露过度拒绝：

| 场景 | 期望 | 实际 |
|---|---|---|
| A 真实单条通知（1 次请于） | 1 条 | 1 条 ✅ |
| B 三条有标题无空行 | 3 条 | 3 条 ✅ |
| C 多请于无边界 | 拒绝 | 拒绝 ✅ |
| **D 单条通知含 4 项任务、每项都有请于** | **1 条** | **拒绝** ❌ |

根因：新判据第一条规则为「请于 ≥4 次且长度 > 100 即拒绝」。
真实的单条通知常在一件事下分列多项、每项各带时间，必然命中，功能等于不可用。

**这是 Dec-021 的另一面**：宁缺勿滥不能走向「把真答案也拒掉」。

## Prompt 正文

```
上次那个分不开的判断改完以后，十八条全过了。不过我又拿了几条真实的通知试了试，发现有个情况不对。
有一条通知是这个样子的，开头写着关于期末教学检查各项材料报送的通知，下面列了四项任务，每一项都写了请于什么时候之前报送什么材料。这明明就是一条通知，四项任务都属于同一件事，结果程序说分不开，把它拒绝掉了。
我猜是这个原因。四项任务里每一项都有请于这两字，加起来出现了四次，程序就把出现四次以上的当成好几条通知了。可是真实的通知经常就是这么写的，一件事下面分成好几项，每一项各有各的时间。要是这样的全被拒绝，这个功能基本就没法用了。
所以现在的问题不是它不够严，而是它太敏感了。真正分不开的确实要拒绝，但是本来就是一条通知的不能跟着一起拒。这两边要同时顾上，你能不能想个办法把它们区分开。
我有个不成熟的想法，如果这几项前面带了一、二、三、四这样的编号，那它们多半属于同一条通知。但这只是我猜的，你来判断，怎么处理都行。
还有一件事。你要是加新的测试条例，把这种一条通知里面带好几项任务的情况也加进去，以后再改判据就不会又把它拒掉了。
最后提醒一下，你每次改 package.json 的时候，里面原来就有的命令要都留着。我上一轮刚加的一个查余额的命令，这次又被你删掉了，这是第二次了，别再删了。
老规矩。脚本要有期望值和通过失败的统计，故意错的用例还要能报红。不要为了这些装新的库。
这一步就只修太敏感这个问题，批量粘贴的其他地方都不要动。相关的代码给我，我在 VS Code 里粘。
```
