# 008 内置日历视图

**提出时间**：2026-10-31 14:20
**提出背景**：用户在浏览器验收 007 五轮收敛结果时主动提出。此前 004 做的是导出 ICS 文件，
用户需要下载文件再找别的软件打开，链路断了。用户认为这一步太麻烦，不符合真实使用习惯。

## 为什么这个需求值得做

1. **演示闭环**：评委从头到尾不用离开页面，一屏说清产品价值，004 的 ICS 链路演示成本过高。
2. **对应评分项**：用户体验与产品精细度 15%，解题有效性与实用价值 25%。
3. **数据现成**：localStorage 已存 deadline 时间戳、location、materials，不需要新的数据源。

## 本条 Prompt 埋的关键点

| 意图 | 写法用意 |
|---|---|
| 让学生自己提出「数据源要不要再存一份」 | 一致性意识，且是真困惑不是演的 |
| 让学生犹豫「下载按钮要不要删」 | 保留 RFC 5545 工程证据，同时避免功能重复，交由 AI 判断 |
| 明确不装新依赖 | 复现成本控制，是用户真实顾虑不是技术术语 |
| 主动提跨月、闰年、每月天数不一 | Dec-013 类缺陷的预防，由学生先想到 |
| 要自检脚本 + 故意失败用例 | Dec-022 / Dec-024 的固定动作，防止再次用肉眼验收 |
| 禁止改动其他功能 | 范围控制，防止 AI 顺手加拖拽编辑 |

## Prompt 正文

```
这次不说故障了，我想加一个新功能，你帮我看看合不合理。

现在解析完要导出日历的话，得点那个下载按钮，它会存成一个文件到电脑上，然后我还得去找别的软件打开它才能看到日程。我觉得这一步太麻烦了，同学真用起来肯定不愿意这么干，文件下载完往往就找不着了。

我想能不能在我们自己的页面里面直接有一个日历。左边那一列通知的上面加两个小标签，一个写通知列表，一个写日历，点一下就切过去。切到日历以后能看到一个月的格子，那天有事的格子上显示个小圆点或者几个字的标题，点那个格子就能看到那天所有的事，什么事、几点、在哪、要带什么东西。没事的日子就空着。

这样做我觉得有两个好处。一个是用户从头到尾不用离开我们的页面，演示的时候一屏就能说清楚我们在干什么。另一个是到月底一眼就能看出哪几天比较忙。

有几个地方我想请你帮我拿主意。

一个是数据来源。日历里显示的这些事，是直接用左边已经存下来的那些通知就行，还是要单独再存一份？我倾向于直接用那一份，我觉得存两份迟早会不一致，但我拿不准，你给个建议。

另一个是以前那个下载日历文件的按钮。我不确定是不是应该删掉，换成这个内置日历。我有点犹豫的原因是，那个文件是符合通用格式的，所有日历软件都能打开，也算是我们做的一个证明。内置日历方便日常看，下载文件方便导到手机里，我觉得两个都有用比较好，但会不会显得重复，你看着办。

还有一个顾虑。我不想为了这个日历去安装新的库，那样以后别人拿到我的项目又得多装一个东西，万一跑不起来就麻烦了。如果基础的办法能算出来，就用基础的办法。

另外有一类坑我提前说一下。算一个月的格子的时候，会碰到跨月、闰年、每个月天数不一样、还有上个月的尾巴占着本月第一格这种情况，很容易差一天。这种错误肉眼看不出来，得等到快到日子才发现。能不能给我一个能在终端直接跑的自检脚本，专门验证这几个特殊情况，比如二月、跨年的十二月、一号正好是星期天、还有每个月天数不一样这几种。

脚本要有期望值和通过失败的统计，还要有一条故意算错的用例，证明这套断言真的能抓到错。上次我们已经验证过这个做法是管用的，我希望这次的日历也能用同样的方式验收。

老规矩，正则里的数字写成零到九这种字符类的样子，不要用反斜杠，我们之前在这个地方连续栽过跟头，我不想再来一次。

这一步就只加内置日历这一件事，通知的编辑、拖拽改日期、重复日程这些统统不要，现有的那几栏布局也不要大改。相关的代码给我，我在 VS Code 里粘。
```

## 验收要点

1. 切换到日历后，本月所有已保存通知按天落到对应格子。
2. 点格子展开当天全部事项，含时间、地点、需带材料。
3. 跨月格子（上月尾巴、下月开头）不串月。
4. 终端脚本：特殊月份用例全绿 + 故意错误用例必须报 FAIL。
5. 保留下载按钮，不得删除。
