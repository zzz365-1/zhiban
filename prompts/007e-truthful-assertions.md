## 缺陷一（严重）：测试归一化把垃圾值洗成空值，失败被算成通过

`normalizeDate` 遇到无法解析的字符串就返回 null；期望值也是 null；两者相等判定通过。

实际表现：

| 编号 | 用例 | 期望 | 实际界面值 | 判定 |
|---|---|---|---|---|
| 3 | 本月25日 | 空 | 本周 | 判为通过（实为失败） |
| 16 | 催缴学费 本月25日 | 空 | 本月 | 判为通过（实为失败） |

本机已确认 `normalizeDate("本月") === null`，与期望 null 相等。

推论：**失败用例不会报错，反而显示为绿。** 这比之前脚本失真更隐蔽。

## 缺陷二：本地规则截断日期

同一条通知「务必于本月25日前完成缴费」，本地规则抽出的 deadline 是 **「本月」**，
后面的 25 日被丢掉。本机验证：

```
本月25日 → deadline=本月   isFuzzyDate=false
本月底  → deadline=本月底  isFuzzyDate=true
本周五  → deadline=本周五  isFuzzyDate=true
```

「本月」既不是完整日期，也不被判定为模糊，**有机会绕过模型兜底直接上屏**。
这是 Dec-021「虚假非空」的同类问题。

## 缺陷三（观感）：终端里通过失败符号显示成问号

Windows 终端编码下 √ / ✗ 输出为「？」，录屏时一屏问号，观感像坏了。
建议改用 PASS / FAIL 之类纯英文字符。
