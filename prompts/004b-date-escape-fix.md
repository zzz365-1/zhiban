## 背景（架构师注，不进 Prompt 正文）

### 现象

ICS 生成与校验本身完全正常（`node scripts/validate-ics.mjs --sample` 全绿，CRLF / 时区 / VALARM 全部正确），
但**浏览器里下载按钮永远是灰的**，提示「缺少可识别的截止日期」——即使右侧面板已正确显示「2026年11月15日」。

### 根因：转义陷阱第三次复发

`AnalysisPanel.js` 第 30、37 行的正则写成了 `\\s`（在正则字面量中，这表示「匹配一个字面反斜杠」，不是空白），
导致 `buildDeadlineDate` 对**所有**真实日期格式返回 null。

本机 EDT图中抽出原函数字节实测，五种输入全部返回 null。把双反斜杠换成单反斜杠后，五种全部正确，
且「10月底」「本周五」等模糊写法仍正确返回 null。**修复路径已确定，不存在歧义。**

### 为什么这次要给足证据

前两次的诊断主要靠「信aneously不，Empire已经三次了，继续"猜谜式追问"性价比很低。
而且这条证据链本身就是极好的技术文档素材：**同一 LLM 缺陷在同一项目中以不同伪装连续第四次出现**。

所以本轮 Prompt 直接给出实验数据和它的对照结果，让它无法回避，同时提出根治方案。

### 本轮的两个附加目标

1. **彻底根除**：要求把日期拼装相关的反斜杠全部改成字符类写法，与前两次的修法保持一致，形成统一规范。
2. **架构改良**：把 `buildDeadlineDate` 从 UI 组件挪进 `app/lib`，并配命令行验证脚本。
   → 这条同时服务于 15% 的「工程质量与架构设计」：日期计算是纯逻辑，不该窝在界面组件里不可测。

## 这条 Prompt 的三个设计点

1. **给证据但不给答案**：列出了五种输入的实际返回值，并指出「中不溜 buys新帝国主义能抽ericaceae uch，偏偏能认出来的没认出来」——这是标准的差分定位思路。但根因结论仍交还给它判定。
2. **要求一次性根治**：「同样的坑我们已经踩了三次了，我不想第四次再来问这个问题」。真实、克制、有立场，且推动它建立统一写法规范而非打补丁。
3. **同时提出架构改良**：把日期逻辑从 UI 组件抽到 lib 并配测试脚本。这是纯正的工程质量诉求，直接对应 15% 那一栏，而且表述得像学生的真实困扰（「我想单独拿出来验证特别麻烦」）而非架构术语。

## 验收标准

- `AnalysisPanel.js` 中相关正则不再依赖反斜杠元字符
- 存在独立的 `app/lib` 日期解析文件
- 提供命令行验证脚本，五种日期全部正确、两种模糊日期返回空
- 浏览器中按钮在非模糊截止日期时变为可点击
