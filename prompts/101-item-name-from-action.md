# 101 事项名称按原文动作生成

## 背景

有两条通知，一条是请全体团员于11月9日前完成本季青年大学习网上主题团课，
另一条是请各位同学于11月12日前登录教务系统核对个人学籍信息。
两条都没要求交任何材料，可拆出来的事项都叫提交材料，卡片上还建议提前把要提交的内容准备好。
演示时一看就不对，名称必须照通知实际让做的事来起。

## 本机已核验事实

本机实跑生产模块，切句与事项名如下。

A1 原文两行，标题是关于本季青年大学习网上主题团课的通知，
正文是请全体团员于11月9日前完成本季青年大学习网上主题团课。
切句得到两句，标题句 kind 是 null，正文句 kind 也是 null，
整条走零事项兜底路径，最终事项名是提交材料，材料数组为空。

A2 正文是请各位同学于11月12日前登录教务系统核对个人学籍信息，逾期不再受理。
同样走兜底路径，事项名提交材料，材料数组为空。

同类新说法，请各位同学于11月20日前完成缴费，事项名也是提交材料。
请各班班长于11月8日晚7点到行政楼A302会议室到场签到，事项名是参加会议。

助学金通知三行，交表那句 kind 是 submit，评审会那句 kind 是 event，
走主路径，事项名分别是提交纸质申请表和参加评审会，材料分别是纸质申请表和空。
这两个名称是对的，本轮不许改。

两条路径都调用同一个 buildName 函数，传四个参数，
第一个是是否手续类，第二个是材料名字数组，第三个是这一小句的原文，第四个是分类。
所以只改这一个函数及其辅助就能覆盖两条路径。

app/lib/noticeItems.js 里当前的相关实现
第269到278行 cleanNameCandidate，去掉句尾标点和开头的呼语前缀。
第281到283行 NAME_VERB_RE，动词表是 提交 报送 上交 递交 缴纳 填写 办理 领取 归还 补交 报名 参加 出席 到场 签到。
第286到298行 EVENT_NOUNS 活动名词白名单与 pickEventNoun。
第345到381行 buildSuggestions，建议对象带 source，值来自 SUGGESTION_SOURCE_SYSTEM。
第383到408行 buildName，手续类有材料就返回提交加材料名，
含报名返回提交报名表，含领取返回领取材料，其余一律返回提交材料，
活动类按活动名词返回参加某某，再不行返回参加活动。
第628到633行主路径调用 buildName。
第750到755行兜底路径调用 buildName。
第743到749行兜底路径的 namedKind 判定，A1 与 A2 都判成 submit。

界面上事项卡已经有通知要求和系统建议不是通知里的要求两个区块，
建议区每条还带系统建议小标签，这一层区分已经做好，不要动。

## 验收要点

第一，A1 的名称要含完成与团课这类原文动作和对象，A2 的名称要含核对与学籍信息，
两条都不能出现提交材料，也不能凭空生成含提交字样的名称。

第二，助学金那条的提交纸质申请表与参加评审会一个字不变，
各自的时间地点材料也不变，这是回归红线。

第三，同类新说法要能通用处理，比如完成缴费得到含完成缴费的名称，
到场签到得到含到场或签到的名称，不许给这几条样例写死判断。

第四，原文没有提交要求时不能生成提交材料这个名字，
实在判断不出动作时，用一个谨慎贴合原文并且自带待确认字样的名称，
让同学在界面上一眼看出这里需要自己核一下，别硬造一个像答案的假名称。

第五，系统建议与通知正式要求的区分保持现状，不要改建议区。

第六，正则一律用字符类，不要出现反斜杠加数字。只输出成对改动片段，
不重写整个文件，不要新建名字差不多的模块。
