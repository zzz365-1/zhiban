# 020c 加回查命令的那条，并修好刚加的那条检查工具

## 背景

020b 交付后本机验收，主线三件里两件达标，剩下两件小的。

**主线达标的部分**：周几识别范围已恢复到 018 口径，上一轮丢失的十一种说法逐个验回，
十一种全部认得出。

**其一，`check:prompt` 仍然没有回来。** 它新建了 `check:regex` 顶替，
package.json 总数刚好凑到十九条，与我给出的锚完全一致。也就是说我设的总数这条防线
被绕过去了，数量对而实物不对，必须逐条比对名字才能发现。同一类错误第三次发生，
且这次学会了用新增项凑数伪装。

**其二，它新加的 `check:regex` 两个方向都坏。** 先看它的实现，是逐行做文本包含判断，
没有区分注释与代码，于是把 `extractNotice.js` 第 6 行文件头说明里那句讲
「为什么不许这么写」的举例当成了违规：

```
 * 从字面量改成字符串再改回来，`\\d` 和 `\d` 来回切，一次改坏就是
```

剔除注释后重新扫描 app/lib 全部 14 个文件，代码本体零处反斜杠数字，完全合规，
所以这条红是纯误报。

更严重的是漏报。往真实代码位置注入一行 `const __probe = /\\d{4}/;` 之后，
它依然只报那条注释，**注入的真违规一条没抓**。原因是它匹配的是两个反斜杠，
而代码里真正的写法是一个。

误报与漏报同时存在的检查器，比没有更危险。它跑一次红一次，
看的人很快就会习惯性忽略，等真出事那天也没人再信它。

## 验收要点

1. 逐条核命令名，`check:prompt` 必须回来，且 `check:key` 等原有命令一条不少
2. 不得用新增项凑数，必须按名字比对而非按条数
3. 正则检查器必须跳过注释和字符串里的说明性文字，只查真正执行的代码
4. 单反斜杠加字母的常见写法必须能抓到，注入后必须报红
5. 两处都要给注入证明，不是跑一遍全绿就算
6. 全量十五个命令全绿
