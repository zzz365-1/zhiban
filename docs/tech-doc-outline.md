## 各章要点

### 封面与摘要，第 1 页

作品名「知办 zhiban」，副标题「校园通知行动助手」，赛事名，作者，日期。
摘要三句话说清楚：把通知拆成可核对的办理路线；
只在必要时调用模型，其余交给确定性代码；
无密钥也能完整体验。摘要里只放三个数字，且必须是实测的：
27 条离线校验命令全绿、48 条评测语料、无密钥降级路径截止日期 84/91。
不写「准确率 95%」这类没有口径的数字。

### 一 问题背景与用户场景，第 3 至 4 页

- 校园通知的四个真实痛点：一条通知里有多件事、时间写法五花八门、
  材料要求散在长句里、发完还会再发补充通知改安排。
- 用户旅程：收到通知 → 想知道要做什么、什么时候、去哪、带什么 →
  怕漏、怕记错、怕补充通知来了没看见。
- 问题边界：这不是通用文档理解，是面向「行动项」的窄任务。
- 引一句真实语料，用 `docs/eval-cases.json` 里的 D01 助学金通知，
  说明一条通知里其实有两件事，截止和活动开始是两种不同类型。

### 二 目标与非目标，第 5 页

目标：可核对、可修正、可复现、无密钥可用。
非目标，明确写出来，避免被当成缺陷：
不做多用户与云同步、不做通用语义理解、不自动修改官方通知里的时间、
不替用户假设活动时长、不收集个人信息。
这一页直接引用 README 第八节已知边界，保持口径一致。

### 三 总体架构，第 6 至 7 页

- 一张架构图：浏览器 UI → `app/page.js` 编排 → 三层逻辑
  （规则抽取 `extractNotice.js`、事项层 `noticeItems.js`、事件层 `routeEvents.js`）
  → 三个出口（办理路线、日历、提醒）；
  旁边单独画服务端 `/api/parse`，只做模型调用，不接触业务数据。
- 关键决策：模型是可选增强，不是必需依赖。
  `parseOne.js` 先跑本地规则，规则结果够好就直接返回，只有不够好才调模型；
  调用失败带错误码降级，界面显示「解析失败」或「本地识别」。
- 技术栈表照抄 README 第五节：Next.js 16.3.8、React 19、Tailwind CSS 4.1.0、
  Node 20.9 以上、DeepSeek 生产用 `deepseek-flash`、代码生成对话用 `deepseek-chat`。
- 数据位置：浏览器 `localStorage` 键 `zhiban.notices.v1`，零数据库。

### 四 数据模型，第 8 至 9 页

- 通知对象 `schemaVersion = 2`，`analysis.items` 是事项数组，
  外层另有 `history` 数组存修改历史。
- 事项字段表：`name`、`timeType`（`deadline` 办理截止 / `start` 活动开始）、
  `date`、`dateText`、`time`、`endTime`、`location`、
  `materials`（对象数组，含 `name` 与 `ready`）、`progress`、
  `status`（每个字段 `ok` / `not_mentioned` / `pending` / `not_applicable`）、
  `evidence`（含 `quote` 与定位区间）、`suggestions`。
- 强调三处约束：多字段必须同源成对，日期和时间不能各取各的；
  新增字段要过四关（抽取、提示词、合并、界面渲染）；
  `endTime` 只有活动类才抽，截止类一律留空。
- 一张迁移图：老数据读入时按原文补出事项，原有字段一个不动。

### 五 核心方法一，确定性代码优先，第 10 至 12 页

- 相对日期：「下周三」「三天后」交给 `relativeDate.js` 本地换算，
  实测早期交给模型约 1/20 概率算错，temperature 设为 0 也消除不了。
- 时间区间与结束时间：只认「开始时间加连接符加结束时间」的完整区间，
  连接符七种，时段词继承，结束必须严格大于开始，跨午夜返回空。
  用 `docs/eval-report.md` 的 D13、E11、E17 三个例子说明。
- 规则抽取：字符类正则，禁止反斜杠加数字的写法，
  `npm run check:regex` 守着这条规矩。
- 为什么不用 RAG、Fine-tuning、Function Calling、多轮记忆、本地部署：
  一段话各一句，理由分别是无检索需求、标注不足、单步不需工具链、
  每条通知独立且贵、本机跑不动。落到那句总结：
  **用最小的模型能力解决最大的语义难题，其余交给确定性代码。**

### 六 核心方法二，出处核对与反幻觉，第 13 至 14 页

- `grounding.js`：模型返回的日期、时间、地点、材料、面向对象必须回原文找到依据，
  找不到即置空并记入 `_groundingDropped`。
- 归一化对照表：展示值 17:00 要能定位到原文的「下午5点」，
  19:00 定位「晚7点」，18:30 定位「晚6点半」，
  `evidence.js` 把原文所有时间说法折算成 24 小时制再反查。
- 点结果字段高亮对应原文，界面上真的会选中那一段。
- 两条实测：`test:grounding` 41 条、`test:locate` 8 项全绿；
  031 的 100 条批量测试里出处核对剔除过值 2 条，是防线生效不是失败，
  数字见 `docs/batch-report-031.md`。
- 诚实写清：出处核对只核对「应该从原文抄」的字段，
  标题、摘要、分类是模型组织出来的，不核对。

### 七 核心方法三，事项化与办理路线，第 15 至 16 页

- 一句一切，先对这一句抽真实值再交给依据模块，抽不出日期就不生成事项。
- 时间轴卡片：名称、时间类型与日期时间、地点、材料清单、状态；
  材料逐条可勾，完成可撤销，刷新保留。
- 通知要求与系统建议用不同区块和标签分开，
  不擅自给事项加原文里没有的限制条件。
- 待确认：日期地点不明标 `pending`，可就地改，改完不再显示「原文未提及」。
- 同源：主页面统一算一次 `routeEvents` 传给工作台与日历，
  避免 earlier 版本「界面标完成日历还显示待办理」的两份数据问题。
- 验证锚：`test:items` 47 条、`test:route` 20 条全绿；
  真浏览器验收「交表办完，评审会仍是待办理」。

### 八 核心方法四，补充通知与日程冲突，第 17 至 19 页

- 补充通知流程：导入 → 手选原通知 → 变化前后对比与依据原句 → 确认 → 更新。
  未提及的字段保留，歧义先确认不覆盖，已完成事项保留，新增材料单独提示，
  每次更新写 `history`，刷新不丢。
- 变更抽取：`noticePatch.js` 四个纯函数，
  `buildNoticePatch`、`matchPatchTarget`、`buildPatchReview`、`applyPatch`。
  两处真实误判修复要写进去：「逾期不再受理」「时间另行通知，地点待定」
  都曾把普通通知劫持进关联流程，`test:patch` 现在 26 条全绿。
- 冲突提醒：`conflict.js` 三种提醒，`overlap` 时间冲突、`cluster` 截止事项集中、
  `needEndTime` 结束时间待补充。严格小于判定，
  一项 16:00 结束另一项 16:00 开始不算重叠；
  只有开始时间不假设时长；同一天多个截止不叫冲突。
  每条提醒有稳定 key，界面靠它去重，不重复堆叠。
- 变更后重算：确认更新后针对那条通知重算提醒，
  成功提示写明「提醒已按新安排重新计算」。
- 验证锚：`test:conflict` 29 条全绿，注入把 `Math.min` 改成 `Math.max` 精确报红 3 条，
  还原后与注入前独立干净副本逐字节一致。

  补充通知与日历同步（047 返修一轮、048 返修一轮且 AI 纠正了学生一次期望值、

- 写明两条方法论：测试脚本必须 import 生产模块；

### 十二 实际限制与后续，第 27 页
