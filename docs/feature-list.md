## 一、产品定位

把一条校园通知，变成一件可以立刻执行的事：粘贴原文，拆出要办的事项、时间、地点和要带的材料，排成可核对的办理路线，同步到日历，并在补充通知到达时对比新旧安排。

三个刻意的选择：**不注册登录**、**不上传原文到服务器**、**没有模型密钥也能跑完整条流程**。数据只存在本机浏览器。

## 二、功能全景

### （一）入口与页面结构

1. 欢迎页：「进入工作台」或「体验示例」。示例数据带「示例」标签，只往前插，不清空自己保存的通知。
2. 左侧四个视图：**工作台、我的通知、日历、变更记录**；侧栏另有「待确认／即将截止／待办理」三个统计快捷入口。
3. 顶栏：搜索通知、分类下拉筛选、整理成文字、载入示例通知。
4. 新增通知弹窗：单条通知／多通知两种模式、原文输入、选填**通知发布日期**、开始解析。日期写错会显示中文报错并禁用解析按钮，不会沿用上一次的合法基准。
5. 详情页是**原文在上、解析结果在下**的上下分区，原文区可折叠，内容多时各自滚动，不留大面积留白。

### （二）通知解析与出处核对

1. **两条路径**：本地规则引擎负责确定性抽取，配置密钥后由 DeepSeek 补充开放式语义抽取；模型不可用或调用失败自动降级，来源标签显示「本地识别」。失败会给出具体原因，原文完整保留，不会假装成功。
2. **抽取字段**：截止日期与时间、活动日期与时间、结束时间、地点、需交材料、面向对象、分类、摘要。
3. **事项拆分**：一条通知可拆成多个事项，每项有名称、时间类型（截止／开始）、日期时间、地点、材料、办理状态与原文依据。一条通知里「报名截止」和「活动举行」两个日期分开管，不串台；纯告知类通知拆不出事项就给空态，不硬造待办。
4. **相对日期换算**：以用户填的**通知发布日期**为基准，由本地确定性代码换算。填 `2026年11月3日` 后「下周三下午4点」显示 `2026年11月11日 16:00`；留空则保持「待确认」，绝不按当天日期偷算。这一条与是否接模型无关。
5. **回原文核对**：点解析结果里的字段，上方原文区自动选中对应那句话。标题也能点回原文首行高亮。模型给的值回原文找不到依据会被置空；换算出来的时间（如原文写「下午5点」而结果写 `17:00`）给中文换算说明，不误报成错误。
6. **人工修正**：原文改动会挂「内容已修改，待重新解析」；字段可手动改，来源标签跟着变成手动。

### （三）办理与跟踪

1. **事项清单**：材料逐项勾选、标记完成／撤销完成、无需办理／取消无需办理、事项字段编辑。
2. **工作台**：待确认、即将截止、待办理三块，统计卡可点进去定位事项；临近截止显示「剩 N 小时」倒计时。
3. **日历**：月视图、翻上月／下月、点某一天看当天安排，按办理状态着色。日历和待办由同一份摊平事件生成，不会各说各话。
4. **日程提醒**：时间冲突、同一天截止事项集中、结束时间待补充。只有两项活动都有明确开始和结束时间才算重叠，一项结束等于另一项开始不算撞车，绝不假设活动一般开多久。
5. **整理成文字**：最近三天／七天汇总成一段可直接发班群的文字，一键复制。
6. **搜索与筛选**：顶栏按关键字搜索，按分类下拉筛选。

### （四）批量与补充通知

1. **多通知批量**：整段粘入多条通知 → 弹窗提示「识别到 N 条通知」→ 逐条解析 → 结果页每条一块、**自带「保存 N 条到我的通知」按钮** → 一次落盘，每条各自带事项清单。另有重复导入查重提示。
2. **补充通知**：识别为补充通知后**由用户手选要修改的原通知**，逐项展示变化前／变化后／依据原句，可「保持原样」或「确认更新」。取消只打标记不删除，已完成事项不回退，未提及的字段保留。
3. **变更记录**：每次确认更新留一条历史，可回看当时的补充通知原文并跳回原通知。

### （五）数据安全与工程复现

1. 通知数据存在浏览器 `localStorage` 的 `zhiban.notices.v1`，刷新保留；换浏览器或清缓存会丢，这是刻意选择，不收集个人信息。保存失败有提示条与「再试一次」。
2. 模型密钥只在服务端 `/api/parse` 读取，不进代码、不进仓库、不上界面。
3. 全部校验命令离线运行、零网络零密钥；提示词与返修往返全部归档，提交历史按细粒度拆分。

## 三、四个核心设计

1. **用最小的模型能力解决最大的语义难题，其余交给确定性代码。** 模型擅长理解自然语言，不擅长算术，也不保证不编造；日期换算、事项切分、日历构造、冲突判定全部由本地纯函数完成。
2. **相对日期本地算。** 早期交给模型换算，「下周三」约 1/20 概率算错，把 temperature 设为 0 也消除不了；现改为 `relativeDate.js` 的确定性换算，提示词要求模型原样返回相对说法、不要自己算。
3. **模型输出必须回原文溯源。** `grounding.js` 把模型返回的日期、时间、地点、材料、对象回原文找依据，找不到即置空并记录原因。「不许编造」只是提示词里的要求，代码里回查才算约束。
4. **不自动改官方通知。** 补充通知必须手选原通知、看过前后对比、点确认才落盘，每次更新留痕。

历史实测成本：单次解析约 0.04 分、耗时 2.0–2.4 秒；批量 100 条时单条平均 0.74 秒。这几项是此前批量测试留档的结论，2026-11-04 未重跑。

### （二）尚未验证，不夸大

1. 补充通知对比逐项决定、日历文件导入手机、跨天刷新这三条只由离线用例覆盖，本轮浏览器未逐条重跑。
2. 浏览器验收用的是 Edge 无头 CDP，不是真机，也没有测移动端窄屏。
3. 无密钥纯本地规则降级路径本轮浏览器没有单独造场景，由离线断言与覆盖率命令覆盖。
4. 时间冲突、截止事项集中、结束时间待补充三类提醒有代码与离线用例，但独立画面没实测。
5. 模型两遍输出不一致约 5% 是历史批量结论，本轮未重跑百条批量。
6. 演示视频由学生按录制模板自行录制，尚未产出成片；技术文档 PDF 仍在准备中。

## 五、已知边界

1. **手动编辑解析字段后，事项清单、日历、待办、冲突提醒不会同步重算。**
2. 补充通知改期写回的是原文写法，未归一化、未重算 `deadlineDate`，跨年与中文数字日期会丢。
3. 补充通知对比弹窗「依据原句」的下标基准与高亮目标不是同一段文本。
4. 模式不匹配提醒计算出来了，但界面没有渲染入口。
5. **界面没有 ICS 下载入口**，日历文件生成与校验只有命令行 `npm run export:ics` / `validate:ics`。
6. 1920×1080 下多通知结果页右侧留白；换算说明沿用红色提示条，观感偏像报错。这两项是视觉层面，不影响功能。
7. 部分相对说法（「半个月后」）、区间日期、周期性时间、「原定 X 推迟至 Y」的改期语义，本地规则尚未完全覆盖。
8. 数据只存本机浏览器，没有云同步，换设备不会带过去。

完整 11 条清单与「本轮明确不修」的说明见 `docs/self-check-2026-11-04-round6.md` 第五节。

## 六、十分钟复现与演示

```bash
git clone https://github.com/zzz365-1/zhiban.git
cd zhiban
npm install
npm run dev
```

浏览器打开 http://localhost:3000 ，首次访问点「进入工作台」。**配置密钥这一步可以整步跳过**，应用照常启动，来源标签显示「本地识别」，核心流程全部可用。
