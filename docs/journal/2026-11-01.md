## 013 面向对象与需提交材料接入模型兜底（提交 cb16bbe）

用户截图反馈：一条含「所有同学，都要参加」「@所有人」的通知，右栏面向对象显示未识别。
本机 grep 定位三处叠加，是 Dec-020 最彻底的一种形态——**从源头就没让模型输出**：

| 环节 | 实际情况 |
|---|---|
| 提示词 | parsePrompt.js 给模型的字段清单只有 title、deadline、time、location、summary、category，**从来没有 audience 与 materials** |
| 合并逻辑 | aiExtract.js 写死 `audience: base.audience \|\| null`，模型结果一律丢弃 |
| 本地词表 | 只认「全体X」「全校X」「各X」「本科生」，不认「所有同学」「所有人」「@所有人」 |

探针实跑确认：「全体同学」「全校学生」「各班班长」能认，「所有同学」「@所有人」返回 null。

**最讽刺的一点**：同一条通知的模型摘要里明明白白写着「全体同学于10月31日上午八点在图书馆报告厅集合参加选举」，
说明模型理解了，但字段格永远空着。这就是 Dec-030 的自查口诀——拿摘要对照字段格，
摘要里提到了而字段为空，必是三关中某一关断了。

修复后三关全通：提示词有要求输出、合并逻辑整套采用不拼接、界面有渲染。
真实 API 实测 materials 三样全中、audience 为「所有人」，旧用例全体同学/全校学生/各班班长未被改坏。

顺带排除一个隐患：max_tokens 只有 1024，怕新增字段后被截断。
实测 `thinking: disabled` 生效，reasoning_content 长度为 0，实际只用了 68 token，
finish_reason 是 stop 不是 length，**不构成隐患**——Dec-017 的教训被这个参数规避了。

## 014 统一粘贴入口与模式一致性校验

用户在讨论中提出：批量粘贴单独放在顶部导航条不显眼，应融合进主输入区。
经三轮讨论定案——**常驻单条/多条模式开关，系统校验内容与当前模式是否相符，不符则提醒，
但决定权归用户**（提醒后用户坚持原模式必须照办，不许偷偷切）。
三条硬约束：它拿不准时就不许提醒（防噪音骚扰）、检测不调模型（用现成 splitNotices，瞬时零成本）、
原批量能力一个不能丢（逐条解析、进度、单条失败不丢弃其余且指明哪条、重复不入库）。
已归档 `prompts/014-unified-input-mode.md`（提交 882766e）。
