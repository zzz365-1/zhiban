### 确认下来的真实情况

框架是 Next.js 16.3.8 的 app router，React 19，样式是 Tailwind v4。
没有后端也没有数据库，通知数据存在浏览器 localStorage，键名 zhiban.notices.v1。
模型调用只有一个出口，前端 fetch 自己家的 /api/parse 接口，
接口里读环境变量 DEEPSEEK_API_KEY 去请求 DeepSeek 的对话接口，
模型是 deepseek-flash，temperature 0，强制 json 输出，超时 20 秒。
密钥没配的时候接口返回 no_key，前端走本地规则，这是无密钥也能跑通的实现方式。
启动命令是 npm run dev，端口 3000。

页面结构是上下两层。顶栏三个标签，待办 日历 全部通知，右边是搜索框 分类下拉 整理成文字。
下面外层是左右两列，左列按标签切换待办列表 日历 通知列表，
右列上下分，上面百分之四十五是输入区，下面百分之五十五是结果区。
输入区分单条通知和多通知两种模式，多通知点解析先弹切分确认，结果在下面结果区按块显示。

### 顺手修的误提

简历和报告会这两处是真误提。讲座介绍简历制作里的简历是讲座内容，
报告会里的报告是活动名，都不是要交的东西。挡法是看前后文，
后面跟地点后缀的挡掉，前面是介绍讲解这类又没有任何提交动作的挡掉。
真要交简历的句子照样能抽出来，这条也写了用例，防止挡过头。

分类那里也有同类问题。行政楼里的行政说的是楼，会议室里的会议说的是房间，
都不能当成这是行政类通知的证据。加了位置拦截，并且给分类标了推断两个字，
让人一眼看出它不是原文抄下来的值。

### 原文依据

展示值十七点整能定位到原文的下午5点，十九点整定位到晚7点，十八点三十定位到晚6点半。

用例里还锁了一条，依据的偏移量切出来的字必须等于引用本身，防止指错地方。

### 日期基准

原来的做法是相对日期一律按今天换算。同学要求缺发布日期时必须提示确认，

整条解析链路也一样，扁平字段会显示明天待确认发布日期，不再给一个假日期。
填了发布日期才换算。两条链路现在口径一致，不会一个显示明天一个显示具体日期。

045 日期地点没定下来的挂待确认牌子，并支持当场改。
空值不算待确认，只有相对日期算不出来和值不合法才挂。
点字段除了跳原文，还就地展开依据原句。

046 日历和待办改成按事项摊平，和办理路线看同一份数据。
新增 routeEvents 模块，日期算不出来的不硬塞，老数据退回整条通知的截止时间，

AI 出的岔子四处。第一处最要命，045 第一版把时间行和字段行写成普通函数却在循环里调用，

第二处是往外传参数漏了事项序号，改就改错地方。
第三处是判断手动改过用了整条通知的来源，颗粒太粗会误伤别的字段的依据。
第四处最隐蔽，046 它把事项字段名猜错了，事项名写成 title、办理状态写成 status，
取出来是空的，是我上一轮没把结构抄全，把真实字段抄给它才出对。
